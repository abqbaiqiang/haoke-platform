# 松茂经营管理平台 V1 数据源与数据质量说明

**版本：** v0.1  
**日期：** 2026-09-08  
**状态：** 第一轮盘点，作为后续数据字典、指标字典和 Codex 开发输入  
**前提：** 不改动精斗云现有业务流程，V1 以手动导入为主，后续预留 API 自动同步。

---

## 1. 本阶段目标

这一阶段不开发页面，先解决三个问题：

1. 系统到底从哪里取数据；
2. 每类数据谁是唯一可信来源；
3. 现有数据缺什么，哪些字段需要在精斗云中补齐。

核心原则：**先把数据口径立住，再做 BI。否则只会得到一套更漂亮的错误。**

## 3. 唯一数据来源（Single Source of Truth）

同一个业务事实只认一个来源，避免 CRM、精斗云、BI 各有一套数字。

| 业务事实 | 唯一来源 | 说明 |
|---|---|---|
| 实际销售订单/成交金额 | 精斗云 | CRM 不允许手工填写真实成交额替代精斗云 |
| 实际商品、商品编码 | 精斗云 | BI 使用商品编码关联 |
| 实际客户编码/客户名称 | 精斗云 | CRM 可增加标签、联系人、备注，但不另造客户交易主档 |
| 实际采购 | 精斗云 | 用于采购、供应商、成本分析 |
| 实际库存 | 精斗云 | BI 只读分析 |
| 实际收付款 | 精斗云/财务口径 | 以后根据可导出字段进一步冻结 |
| 财务营业收入、费用、净利润 | 利润表 | 与精斗云经营销售额允许存在口径差异 |
| 月末现金、应收、存货、负债 | 资产负债表 | 财务月末口径 |
| 客户跟进、商机、待办、关系人 | CRM | 本系统唯一来源 |
| 销售目标 | 本系统 | 管理指标，不回写精斗云 |

## 4. 销售导出数据结构结论

现有销售导出已经包含大量可直接用于数据中台的字段，包括：

- 单据日期、单据编号、销售人员；
- 客户编码、客户名称、客户类别；
- 销售金额、优惠、已收款、收款状态、本次欠款；
- 收款条件、收款到期日；
- 商品编码、名称、型号、条码；
- 长宽高、体积、重量；
- 商品类别、品牌、单位；
- 数量、销售单价、折扣、金额；
- 参考成本、预估毛利、预估毛利率、最近一次采购价；
- 仓库、可用库存、基本单位、整件散包、换算公式等。

### 4.1 特殊结构

销售导出不是严格的“一行一张订单”，而是：

- 订单头字段出现在订单首行；
- 多商品订单的后续商品行，订单字段可能留空；
- 中间存在“合计”行。

因此导入程序必须自动拆分为：

- `sales_order`：一张销售单一条；
- `sales_order_line`：一个商品明细一条。

导入时必须识别并忽略“合计”行，同时把多商品订单的订单头信息正确向下关联。

## 5. 当前最需要整改的商品数据

以下为当前已确认的重点问题，按系统价值排序。

### A+：必须优先完善

#### 5.1 商品分类

当前销售明细中商品分类维护率很低。建议所有在售/有库存 SKU 至少维护：

- 一级分类；
- 二级分类（确有必要时）。

建议一级分类保持少而稳定，例如食品、粮油、家纺、厨具、小家电、杯壶、日用百货、礼盒等。

**用途：** 品类销售、毛利、库存、季节性分析。

#### 5.2 成本体系

至少区分三种成本概念：

1. 最近采购价：用于当前采购和报价参考；
2. 实际历史销售成本/出库成本：用于真实历史毛利；
3. 参考成本/标准成本：用于报价预警，可选。

**禁止直接用“当前最近采购价”反算几个月前的真实销售毛利。**

后续需要确认精斗云是否可导出：销售成本、出库成本、商品收发明细或成本明细。

#### 5.3 基本单位与箱规

建议维护：

- 基本单位（盒/瓶/袋/台/套等）；
- 整件单位（箱等）；
- 每箱数量；
- 整箱重量；
- 整箱长宽高。

**用途：** 库存换算、整箱/散件分析、物流成本、运费计算。

### A：重要完善

#### 5.4 品牌

所有核心在售 SKU 尽量有品牌，避免同一品牌被多种写法拆散。

#### 5.5 规格/型号

同一真实 SKU 应有稳定型号/规格，型号格式尽量统一，例如不要同时存在 `WT4017` 与 `WT-4017` 而未确认是否同品。

#### 5.6 重量、体积、长宽高

销售明细虽然存在这些字段，但大量为 0 或空。对经常发快递/快运的商品，应优先补整箱物流参数。

## 6. 当前最需要整改的客户数据

### 6.1 客户类型

建议客户至少有一个标准“客户类型”，例如：

- 礼品公司；
- 企业直客；
- 经销/贸易；
- 电商；
- 个人/零散；
- 内部/样品。

客户标签（如中国银行、工行、农行、烟草、保险、一件代发）不等同于客户类型，标签由 CRM 管理，可多选。

### 6.2 结算方式与账期

对赊销客户建议维护：

- 收款条件；
- 账期天数；
- 到期规则。

这样系统才能区分“正常未收款”和“已经逾期”。

### 6.3 客户唯一性

客户编码作为系统关联主键。后续新增客户时必须做重复检测，避免同一家公司因简称、全称、不同联系人形成多个客户主档。

## 7. 采购与供应商数据的后续检查重点

目前已收到购货单、供应商档案文件，但为旧版 `.xls`。后续字段级全面体检建议重新导出为 `.xlsx` 或 `.csv`，以便形成准确的缺失率和整改清单。

采购数据重点检查：

- 采购单号、日期；
- 供应商编码/名称；
- 商品编码；
- 数量、含税/未税采购价；
- 采购金额；
- 仓库；
- 付款状态；
- 退货；
- 采购人员；
- 到货日期。

供应商重点检查：

- 供应商编码；
- 供应商名称；
- 联系人；
- 结算方式；
- 账期；
- 主营品牌/商品；
- 启用状态。

## 10. 导入系统必须具备的基础能力

Codex 后续开发数据中心时必须实现：

- 文件原件留档，不覆盖历史文件；
- 自动识别文件类型和数据月份/日期范围；
- 导入前预检；
- 字段映射；
- 数据类型校验；
- 唯一键去重；
- 新增/更新识别；
- 错误行单独展示；
- 可重复导入但不能重复计数；
- 可按日期范围重新同步；
- 导入日志；
- 数据回滚/重跑策略；
- API 接入后与 Excel 导入共用同一标准数据层。

## 11. 数据层初步分层

### RAW 原始层

保存每次上传的原始文件及原始字段，不做破坏性修改。

### CORE 标准业务层

至少包括：

- customer
- product
- supplier
- sales_order
- sales_order_line
- purchase_order
- purchase_order_line
- inventory_snapshot
- receivable/payment（待正式样本确认）
- crm_followup
- crm_contact
- crm_tag
- opportunity
- task
- sales_target
- activity_log

### BI 分析层

按日/月、客户、商品、业务员、供应商等预聚合，用于快速看板查询。

## 12. 当前阶段结论

现有数据已经足够启动系统设计和第一版 CRM/销售 BI，但还不足以一次性冻结完整的采购、库存、应收应付和真实毛利模型。

因此当前开发顺序保持：

1. 先冻结 CRM 与销售 BI；
2. 同时补商品主档和成本相关字段；
3. 获取库存、收付款、退货、成本相关样本；
4. 再冻结经营 BI 的后半部分；
5. 最后接 AI 和精斗云 API。
