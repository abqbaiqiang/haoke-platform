## 2. 已核验的数据条件

- 现有代码有标准销售头及版本明细、来源/批次、CRM 过程实体和活动日志；尚无销售目标模型、工作日历或 M3 查询服务。
- 本轮只读检查确认本地现有销售单全部为 `source_status=unverified`，且存在未映射销售人员。统计证据保存在忽略目录 `app-data/m3-readiness.json`，不在此记录原始公司金额、人员和单号。
- M1 月度汇总是 `DQ_SALES_RECON` 源销售核对，不是已验证的 `EXEC_SALES_AMT`。未核实单据不能静默当成有效经营事实，也不能因过滤后无可用单据显示为真实零销售。
- 退货、作废/取消处理和导出完整范围仍待业务核实。个人销售额不能按当前客户负责人倒推；历史订单必须按 ERP 销售人员归属过滤。
- 商品的可选品牌/分类仍主要保存在来源字段/RAW；需先验证字段映射再做分类分析。未知项保留“未分类”，不能按名称猜测。
- 财务口径独立，M3 不确认财务报表或填写空白；真实成本、采购、库存、应收及 AI 不纳入本阶段。

## 3. 实施顺序与交付

| 步骤 | 实现内容 | 验收重点 |
|---|---|---|
| M3.1 | 月目标、工作日历和参数设置 | 人员/月目标唯一；修改审计；工作日覆盖节假日、调休和人员例外；金额 NUMERIC |
| M3.2 | 个人销售工作台 | 目标进度、剩余目标、今日/本周/逾期待办、商机储备及 CRM 快捷入口；手机可完成操作 |
| M3.3 | 销售聚合与趋势 | 日/月趋势、订单/客户/SKU、环比/同比；明确可用数据范围、基期、截至日和来源更新时间 |
| M3.4 | 客户/商品/业务员分析与贡献 | 排行和下钻；当前及对比期维度全集；Top N 加其他项能解释总变化；版本明细不重复累加 |
| M3.5 | 团队执行与客户关注 | 登录与有效活跃分开；跟进、待办、商机并列；沉睡/疑似流失/同期未复购，阈值可配置 |
| M3.6 | 全量回归及本地交付 | 五角色、越权、幂等、Decimal、迁移、桌面/手机；备份后升级并核对旧数据；同步报告和人工清单 |

界面沿用现有导航和 CRM 操作，图表按架构使用 ECharts。服务端负责所有核心数值计算，前端接收强类型 DTO、格式化和绘图。

## 4. 指标与边界

- 目标：`TGT_MONTH_AMT`、`TGT_COMPLETION`、`TGT_TIME_PROGRESS`、`TGT_PROGRESS_GAP`、`TGT_REMAINING`、`TGT_DAILY_REQUIRED`、`TGT_RUNRATE_FORECAST`、`TGT_WEIGHTED_FORECAST`。目标空/零显示未设置，工作日为零不除零；商机仅纳入预计当月关闭的开放项，金额/概率缺失明确提示预测不完整。
- 销售：`EXEC_SALES_AMT`、`SALE_ORDER_COUNT`、`SALE_CUSTOMER_COUNT`、`SALE_SKU_COUNT`、`SALE_AOV`、`SALE_MOM`、`SALE_YOY`、`SALE_CONTRIBUTION_CHANGE`。基期零与缺失分别表达；当前月注明截至日期，历史覆盖不足不生成同比结论。
- 客户：首次成交/回购/期内复购分别计算；首次成交仅能在已知历史内判断，完整历史未证实需显示限制。集中度按 `ceil(成交客户数 × 20%)`；沉睡与疑似流失不得重叠或自动修改客户人工状态。
- CRM：`CRM_LOGIN_DAY`、`CRM_EFFECTIVE_DAY`、`CRM_ACTIVE_RATE`、有效跟进次数/客户数、到期任务完成率和逾期待办。有效动作集合可配置，浏览与登录不算有效业务动作，作废跟进不计有效跟进。
- 商品：只取当前有效版本明细，统一 SKU/单位后计算数量与均价；不同单位不直接汇成“公司总件数”；订单头与明细存在口径差异时单列差额，不人为分摊制造商品贡献。
- 各指标携带 metric code、数据状态、范围、更新时间和缺失原因；“未验证/未覆盖”不能转换为数值零。

## 5. 权限及数据设计

新增 `sales_target`（人员/月唯一，金额 NUMERIC(18,2)，审计字段）与工作日历/业务参数持久化模型，通过下一条 Alembic 迁移增加。工作日历全局规则与个人日期例外分别保存，参数修改留操作日志。最终表结构在实施时按字段字典核对。

统一经营查询权限与 CRM 过程权限，先应用服务器范围再聚合、排行、计算总数和下钻。老板看全局，经理看团队，销售看本人；财务仅看授权销售数据，不返回个人目标、跟进或商机；管理员只处理运维/配置，不自动取得经营看板权限。受限角色不得通过排名、选项、总数或数据质量提示推知范围外客户和人员。

沿用来源命名空间与当前版本事实，不覆盖旧批次、原件及历史人员归属。小规模数据优先使用 PostgreSQL 查询/View 保证导入提交后立即可见；是否物化由性能证据决定，需物化时刷新纳入导入后流程并测试去重/重算。

## 6. 业务待确认与不受影响的工作

| 事项 | 状态与处理 |
|---|---|
| M2 人工验收/先开发安排 | 当前阶段安排待用户明确；不自动打勾 |
| 有效销售、退货、作废与导出覆盖 | `BLOCKED_BUSINESS_DECISION`：正式经营销售指标启用前核实；可先开发查询、DTO、测试夹具和“数据待验证”状态 |
| ERP 销售人员与账号映射 | 未映射不分配给演示用户；管理员明确映射并留历史后，再展示对应个人实际业绩 |
| 日期覆盖完整性 | 最早/最晚订单日不是完整覆盖证明；导入批次范围和业务确认共同表达覆盖；无订单月份不能据此判断缺失或真实零 |
| 工作日历、沉睡/流失阈值 | 使用指标字典默认周一至周五及 90/180 天初值，允许后台调整；节假日不按推测自动填充 |
| 跟进等级阈值 | 未配置时显示未设置，不擅自定天数；不阻塞其他目标/CRM 指标 |
| CRM 到期任务口径 | 实施前明确取消任务及延期历史对分母的处理；不回写历史制造完成率；必要时配置并说明口径 |

上述销售数据待确认项只限制依赖指标的正式启用，不阻塞目标管理、日历、CRM 过程分析及权限/计算引擎的开发。

## 7. 测试与交付要求

固定样本覆盖 0.1+0.2、目标空/零/超额、工作日零/调休/请假、月初/月末/闰年/跨年、基期零/缺失、期中标签、未知销售状态、取消/退货映射、未分配人员、旧版明细、重复导入后汇总不翻倍、贡献总和、集中度取整、客户关注阈值边界和缺概率预测。

每个数据接口验证 owner/manager/sales/finance/admin 范围，至少包括 S1 请求 S2 明细/修改目标、经理请求团队外人员、财务请求 CRM 过程、管理员请求经营总览，以及总数/排行/下钻一致过滤。空库升级、迁移模型比较、旧数据保留及有数据的降级保护纳入测试。

M0–M3 回归全绿后才记录本地自动验收通过。实际部署仍先备份再 Alembic，并校验账号、旧事实、原件、财务状态与 CRM 历史；人工验收与 Docker/NAS 补验单独记录。
