# 一、当前仓库事实基线

本开发文档基于 2026-09-19 当前 `master`。

现有技术栈：

- PC 前端：Next.js + React + TypeScript
- 图表：ECharts
- 后端：FastAPI + SQLAlchemy + Pydantic
- 数据库：PostgreSQL
- 迁移：Alembic
- 部署：Docker Compose + Caddy
- Worker：已有独立 Worker 进程

仓库已有 CRM 业务模型，不应另建一套移动 CRM。

# 四、为什么建议新增 `apps/miniapp`

不要塞进 Next.js PC 项目。

小程序拥有：

- 不同运行时；
- 不同导航；
- 不同登录凭证存储；
- 微信定位；
- 微信录音；
- 微信媒体；
- 小程序域名要求；
- 移动触控布局。

推荐：

```text
apps/miniapp/
  package.json
  project.config.json
  config/
  src/
    app.tsx
    app.config.ts
    pages/
    components/
    services/
    styles/
    types/
    assets/
```

但是它与 PC 共用同一个 FastAPI 后端和 PostgreSQL。

# 五、小程序技术选择

推荐：**Taro 4.x + React + TypeScript + SCSS**。

原因：

- 与现有 React/TS 思维一致；
- 支持微信小程序；
- 有录音、Map、媒体选择等 API 适配；
- 后续需要 H5 时还有复用空间；
- 比原生小程序重新维护另一套语法成本低。

配置基准建议：

```ts
// config/index.ts
export default defineConfig({
  designWidth: 750,
  deviceRatio: {
    375: 2,
    750: 1,
  },
})
```

项目内统一使用 rpx / Taro 转换规则，不在各页面随意混合尺度。

# 九、认证适配

## 当前事实

PC 登录主要依赖：

- `songmao_session` HttpOnly Cookie；
- 浏览器 Origin 校验。

这个模型不应该直接硬套到微信小程序。

## V1 推荐

增加专用移动认证接口，但继续复用现有用户和 Session 数据。

```text
POST /api/mobile/auth/login
GET  /api/mobile/auth/me
POST /api/mobile/auth/logout
```

V1 小程序用现有用户名 + 密码登录。

登录成功返回随机不可预测的 Session Token，小程序放入本地 Storage，并通过：

```http
Authorization: Bearer <session_token>
```

发送。

后端统一把：

- PC Cookie；
- Mobile Bearer Token

解析为同一种 Actor / Principal。

### 安全要求

不得为了小程序直接关闭整个 Origin / CSRF 保护。

非安全方法的规则应调整为：

- 浏览器 Cookie 请求继续要求可信 Origin；
- `/api/mobile/*` 只接受 Bearer Token，并在 Endpoint 真实鉴权；
- 其他请求维持现状。

后续可以增加 `wx.login()` + 员工账号绑定，但不阻塞 V1。

# 十、后端移动 API 分层

推荐：

```text
apps/backend/app/mobile_api.py
apps/backend/app/mobile_schemas.py
apps/backend/app/mobile_service.py
```

职责：

- mobile_api：HTTP 路由；
- mobile_schemas：移动端 DTO；
- mobile_service：聚合已有 CRM 数据，减少手机端请求次数；
- 核心写操作仍调用 crm_service。

禁止把 `mobile_service` 写成第二个 `crm_service`。

- customer；
- contacts；
- tags；
- followups；
- tasks；
- opportunities；
- events；
- orders；

但是移动端不建议直接把整个 PC Detail DTO 原样拉过来：

# 十三、Worker 的新职责

不引入 Redis/Celery 也能先把 V1 做稳。

利用现有 Worker 增加两类轮询任务：

## 1. 地址地理编码

扫描：

```text
company_address 有值
AND geocode_status = pending
```

调用地图服务解析并保存坐标。

## 2. 音频转写

扫描：

```text
mobile_media_draft.media_type = audio
AND transcription_status = pending
```

完成 ASR 后写入 transcript。

AI 整理可以：

- 转写完成后自动进入 `ai_pending`；或
- 用户点击“AI 整理”时按需执行。

V1 推荐按需执行 AI，减少无意义调用。

# 十四、附近查询不引入 PostGIS

当前客户规模没有必要为 V1 引入新的数据库扩展。

做法：

1. 根据当前位置 + radius 先计算经纬度 Bounding Box；
2. SQL 预筛；
3. 服务层用 Haversine 计算真实距离；
4. 按距离排序；
5. 上限如 100 条。

以后客户量到数万甚至更大，再评估 PostGIS。
