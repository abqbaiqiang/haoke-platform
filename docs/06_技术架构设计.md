# 松茂经营管理平台 V1 技术架构设计

**版本：** v0.1  
**日期：** 2026-09-08  
**部署目标：** 首期可部署于绿联 NAS；未来可迁移普通 Linux 云服务器，不改业务代码。

## 1. 架构目标

V1 优先“稳、易维护、可迁移”，而不是堆技术名词。

- 4~5 名核心用户即可稳定运行，架构可平滑扩展到几十用户；
- 核心功能断开 AI API 后仍完整可用；
- 不绑定绿联 NAS 专有 SDK；
- 不绑定阿里云专有服务；
- Excel/CSV 与未来精斗云 API 共用同一标准化数据入口；
- 数据库、上传文件和备份必须持久化；
- 所有核心业务规则可测试。

## 2. 技术栈

### 2.1 前端

- **Next.js + React + TypeScript**；
- UI 组件优先选成熟、可维护的开源组件库，避免为了“炫”自造基础控件；
- 图表：**Apache ECharts**；
- 表格：支持筛选、排序、分页、列显示控制；
- Web 响应式布局，桌面优先，同时保证手机可完成客户查看、跟进、待办、商机更新。

版本原则：项目初始化时使用当前稳定版本并写入锁文件，后续不随意大版本升级。

### 2.2 后端

- **Python + FastAPI**；
- ORM：SQLAlchemy 2.x 风格；
- 数据校验：Pydantic；
- 数据库迁移：Alembic；
- Excel 解析：pandas/openpyxl；老 `.xls` 支持作为兼容输入，但鼓励转 xlsx/csv；
- 后台任务：V1 使用独立 worker 进程 + PostgreSQL 任务表即可，不强制引入 Redis；未来任务量增大再扩展消息队列。

### 2.3 数据库

- **PostgreSQL**；
- 金额使用 NUMERIC，不使用二进制浮点；
- JSONB 仅用于可变配置/原始内容，不把核心业务字段偷懒全塞 JSON；
- 时间统一 `TIMESTAMPTZ`；显示按 Asia/Shanghai。

### 2.4 部署

Docker Compose 至少包含：

```text
frontend
backend
worker
postgres
reverse-proxy
```

`reverse-proxy` 可使用 Caddy 或 Nginx。优先选择配置简单、HTTPS 友好的方案。

## 3. 逻辑分层

```text
浏览器
  ↓
Web 前端（Next.js）
  ↓ HTTPS/API
FastAPI
  ├ CRM 业务服务
  ├ BI 查询服务
  ├ 导入/标准化服务
  ├ 权限服务
  └ 集成连接器接口
        ↓
PostgreSQL
  ├ RAW / 导入审计
  ├ CORE / 标准业务数据
  ├ CRM
  ├ FINANCE
  └ BI 聚合/物化视图
```

## 4. 数据流

### 4.1 V1 手动同步

```text
精斗云导出 Excel/CSV
      ↓
上传文件与 import_batch
      ↓
RAW 保存原始文件和原始行
      ↓
模板识别/字段映射/数据验证
      ↓
标准化 + 幂等 Upsert
      ↓
CORE 业务表
      ↓
BI 聚合/指标刷新
      ↓
Dashboard
```

### 4.2 未来 API

```text
精斗云 API Connector
      ↓
统一 Connector DTO
      ↓
与 Excel 相同的标准化服务
      ↓
CORE / BI
```

API 接入不得另写一套 BI 数据路径。

## 5. Connector 设计

后端定义统一接口概念：

- `CustomerConnector`
- `ProductConnector`
- `SalesOrderConnector`
- `PurchaseOrderConnector`
- `InventoryConnector`
- `PaymentConnector`

V1 至少实现：

- `JingdouyunExcelConnector`
- `FinanceExcelConnector`

预留：

- `JingdouyunApiConnector`

Connector 输出标准 DTO，由标准化服务写 CORE。页面和 BI 不直接感知 Excel 或 API。

## 6. 导入与幂等

导入必须支持：

- 同一文件重复上传不产生重复事实；
- 同一销售单更新后可更新原单，不新建一份“平行销售”；
- 订单头/订单行拆分；
- 忽略合计行；
- 对关键字段缺失给出明确错误；
- 导入失败不产生半套脏数据，使用事务/批次状态；
- 每个来源记录 `source_key`、`source_updated_at`（有则用）、`import_batch_id`；
- 支持重算 BI，不需要重新人工录 CRM。

## 7. 身份认证与安全

V1 推荐：

- 用户名/手机号 + 密码；
- 密码使用 Argon2id 或 bcrypt 等成熟算法哈希；
- Cookie Session 或安全 Token 方案均可，但不得把长期敏感 Token 放 localStorage；
- 生产环境只允许 HTTPS；
- 登录失败限流；
- CSRF/CORS 按实际架构正确配置；
- 后端统一权限中间层/依赖校验；
- SQL 全部使用 ORM/参数化；
- 文件上传限制扩展名、MIME、大小，并保存到非 Web 可直接执行路径。

V1 暂不需要企业级 SSO。

## 8. 文件存储

目录通过环境变量配置，不写死绿联路径：

```text
/app-data/uploads/raw
/app-data/uploads/attachments
/app-data/backups
```

Docker 映射到 NAS/服务器宿主持久目录。

原始 Excel 必须保存：文件哈希、上传人、上传时间、原文件名、数据源、导入状态。

## 9. BI 架构

- 指标实现以 `04_V1指标字典.md` 为唯一口径；
- 常用日/月聚合可落普通聚合表或物化视图；
- 当前 4~5 人规模不需要引入独立 ClickHouse/数仓；
- BI 查询不得在每次页面打开时重复解析 Excel；
- 当前未完月比较必须标记“截至当前日期”；
- 所有金额、比例基期异常处理按指标字典实现。

## 10. AI 架构

AI 为**可插拔 Provider**：

```text
AI Provider Adapter
  ├ OpenAI-compatible
  └ disabled
```

AI 输入只允许使用：

- 已计算指标；
- 贡献拆解；
- 异常列表；
- 经权限过滤后的客户/商机摘要。

原则：

- AI 不写入核心财务指标；
- AI 不直接对原始 Excel 自行求和后覆盖系统指标；
- 未配置 API 时隐藏/禁用 AI 功能，不影响 CRM/BI；
- 密钥加密保存或通过 Secret 环境变量引用，不打印日志。

## 11. 精斗云 API 预留

后台预留：

- Provider 启用开关；
- Base URL；
- AppKey；
- AppSecret/Token 等密钥；
- 企业/账套 ID；
- 需要同步模块；
- 测试连接；
- 最后成功时间；
- 同步日志；
- 手动“立即同步”和按日期重拉能力。

由于真实精斗云 API 认证/字段要以届时官方文档为准，V1 **只做可扩展接口和设置位，不编造未验证 API 行为**。

## 12. 运行环境与迁移

### 12.1 NAS

- Linux 容器环境；
- Docker Compose；
- 数据库存储、上传文件、备份目录全部 Volume 映射；
- PostgreSQL 端口不暴露公网；
- 外网访问优先通过安全反向代理/HTTPS/VPN 或合适的远程访问方案；
- 不依赖 NAS 私有路径和专有 API。

### 12.2 云服务器

迁移时：

1. 新服务器安装 Docker；
2. 复制 `.env`（重新核验密钥）；
3. 复制/恢复数据库备份；
4. 复制上传文件/附件；
5. `docker compose up -d`；
6. 切换域名/DNS。

业务代码无需分叉为“NAS版”和“阿里云版”。

## 13. 可观测性

至少记录：

- 应用错误日志；
- 登录/权限拒绝；
- 导入批次；
- 后台任务状态；
- 数据源同步日志；
- 关键业务审计；
- 版本号/构建号。

日志不得包含密码、API Key、AppSecret、完整 Token。

## 14. 性能目标（V1）

按当前规模设务实目标：

- 普通 CRM 列表/详情：P95 < 1 秒（局域网正常条件）；
- 普通 BI 首屏：P95 < 2 秒；
- 大型 Excel 导入允许后台处理，不阻塞 Web 请求；
- 10 万级销售明细仍可正常筛选和月度聚合；
- 4~5 人并发使用无明显卡顿。

这些不是互联网大厂 SLA，是为了防止一张客户表打开 8 秒这种不必要的人类磨难。
