# 松茂经营管理平台 V1 数据库物理设计

**版本：** v0.1  
**日期：** 2026-09-08  
**依据：** `03_V1数据字典.md`。本文件补充物理约束、索引、唯一键、迁移和性能规则，不替代字段字典。

## 1. Schema 建议

V1 可采用一个 PostgreSQL 数据库，按 schema 分区：

- `sys`：用户、权限、配置、审计；
- `raw`：导入批次、原始行/原始 JSON；
- `crm`：客户扩展、联系人、标签、跟进、任务、商机；
- `erp`：商品、供应商、销售、采购、库存、应收；
- `fin`：月度财务数据；
- `bi`：聚合表、物化视图、异常结果。

如 ORM 使用跨 schema 增加复杂度，也允许 V1 使用统一 public schema + 清晰前缀，但不得出现含义不清的表名。

## 2. 主键和来源键

- 内部主键：UUID；
- 精斗云客户：`source_system + source_customer_code` 唯一；
- 商品：`source_system + product_code` 唯一；
- 销售订单：`source_system + order_no` 唯一；
- 销售订单行：优先来源行唯一 ID；若没有，使用稳定组合键（订单号 + 来源行序号/商品编码 + 可验证的行标识），不得仅以商品名作为唯一键；
- 采购订单同理；
- 上传文件：`sha256` + data_source 作为重复检测依据之一。

## 3. 关键约束

### 3.1 用户

- `username` UNIQUE；
- `is_active=false` 后禁止新登录；
- 用户被停用不级联删除客户、跟进、商机。

### 3.2 客户

- `source_customer_code` 允许潜客为空；
- 一旦与精斗云绑定，同一来源编码只能绑定一个活动客户；
- 客户合并需保留 merge history；V1 如不实现自动合并，则至少禁止静默覆盖。

### 3.3 联系人

- 联系人不以手机号全局 UNIQUE，因为共用电话/总机可能重复；
- 可建立 `(customer_id, mobile)` 非强制重复提示索引；
- 删除采用 soft delete。

### 3.4 跟进

- `customer_id`、`owner_user_id` 必填；
- 创建时间不可由普通销售任意回写；可有 `occurred_at` 表示实际沟通时间；
- 修改后记录审计版本/差异；
- 软删除。

### 3.5 商机

- 金额 >= 0；
- 概率 0~1；
- 赢单/流失后需有 `closed_at`；
- 流失建议记录 `lost_reason`；
- 阶段变更写审计事件。

### 3.6 销售目标

唯一键建议：`(user_id, target_month)`；如后续存在多目标版本，使用 version + active 标识，但 V1 先保持简单。

### 3.7 销售/采购事实

- 来源订单唯一键必须可 Upsert；
- 金额 `NUMERIC(18,2)`，单价可 `NUMERIC(18,4)`；
- 行金额不得因为 UI 浮点误差改变；
- 来源原始值可在 raw 层保留；
- 取消/作废状态保留原记录，BI 通过标准状态排除，不物理删除。

## 4. 推荐索引

### CRM

- `customer(owner_id, is_active)`；
- `customer(source_system, source_customer_code)` UNIQUE（非空条件）；
- `crm_contact(customer_id, is_active)`；
- `crm_followup(customer_id, occurred_at DESC)`；
- `crm_followup(owner_user_id, occurred_at DESC)`；
- `crm_task(assignee_id, status, due_at)`；
- `crm_task(customer_id, due_at)`；
- `crm_opportunity(owner_user_id, stage, expected_close_date)`；
- `crm_opportunity(customer_id, stage)`；
- `customer_tag_map(customer_id, tag_id)` UNIQUE。

### ERP

- `sales_order(order_date)`；
- `sales_order(customer_id, order_date DESC)`；
- `sales_order(sales_user_id, order_date DESC)`；
- `sales_order_line(product_id)`；
- `sales_order_line(sales_order_id)`；
- `purchase_order(supplier_id, order_date DESC)`；
- `inventory_snapshot(snapshot_date, product_id)` UNIQUE（按实际仓库粒度加 warehouse_id）；
- `receivable_snapshot(snapshot_date, customer_id)`。

### 系统/导入

- `import_batch(data_source_id, created_at DESC)`；
- `import_batch(file_sha256)`；
- `activity_log(user_id, occurred_at DESC)`；
- `activity_log(action_type, occurred_at DESC)`。

## 5. BI 物化设计

V1 不需要复杂数据仓库。建议至少有以下日/月聚合：

- `bi.sales_daily_by_user`
- `bi.sales_monthly_by_user`
- `bi.sales_monthly_by_customer`
- `bi.sales_monthly_by_product`
- `bi.crm_activity_daily_by_user`
- `bi.opportunity_monthly_by_user`
- `bi.customer_last_activity`
- `bi.customer_last_sale`

数据少时也可以用 View + 合理索引；如果查询变慢再物化。不要为了“像大数据”先造十层 ETL。

## 6. 导入事务模型

一个 import batch 建议经历：

`uploaded -> validating -> ready -> importing -> succeeded / partially_failed / failed`

规则：

1. 文件先保存再解析；
2. 预检阶段不修改 CORE；
3. 正式导入以批次事务或分块事务执行；
4. 批次失败时要能识别已提交块，不重复写；
5. 每条 CORE 事实保留 `last_import_batch_id`；
6. 重跑同一来源数据执行幂等 Upsert；
7. 导入完成后触发 BI 刷新任务。

## 7. 软删除和历史

推荐公共字段：

- `is_active` 或 `deleted_at`；
- `created_at`；
- `updated_at`；
- `created_by` / `updated_by`（适用 CRM 写数据）。

禁止把所有历史数据靠“覆盖一行”解决：

- 客户转交 -> history 表；
- 目标修改 -> audit；
- 商机阶段 -> audit/event；
- 库存 -> snapshot；
- 财务月度 -> period + metric；
- 导入 -> batch。

## 8. 配置与密钥

非敏感业务参数可用 `sys_setting`：

- dormant_days；
- lost_warning_days；
- followup_threshold_A/B/C；
- work_calendar；
- 预警阈值。

密钥不要存普通 `sys_setting.value_text`。应：

- 首选环境变量/外部 Secret；或
- 使用应用主密钥加密后落库，并且接口永不返回明文。

## 9. 迁移规则

- 所有 schema 变更必须通过 Alembic migration；
- 禁止生产环境手工改表后“回头补 migration”；
- migration 必须可在空库重建；
- 破坏性变更必须先备份并提供回滚/迁移说明；
- 字段重命名不得通过“删旧建新”导致数据丢失。

## 10. 数据库测试重点

- 唯一键能阻止重复客户编码/订单号；
- Upsert 同一销售单不会翻倍；
- 取消单状态更新后 BI 能排除；
- 删除/停用用户不会删除历史 CRM；
- 权限查询不会跨 owner/team 泄漏；
- NUMERIC 计算与指标字典一致；
- 数据库备份可恢复到新实例。

## M1 落地版本（2026-09-08）

以 Alembic `0002_m1` 为当前可执行结构。来源命名空间、财务月份按来源唯一、不可变批次映射和销售明细版本唯一键的补充见 [M1 验收报告](15_M1验收报告.md)。当前 CORE 查询实时生成月度核对值；后续 BI 物化表及 CRM 表仍按各里程碑实施，不将目标设计误记为已建表。
