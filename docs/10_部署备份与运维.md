# 松茂经营管理平台 V1 部署、备份与运维

**版本：** v0.1  
**首选生产环境：** 绿联 NAS + Docker Compose  
**迁移目标：** 任意标准 Linux 云服务器（如以后使用阿里云）。

## 1. 环境区分

至少区分：

- `development`：开发；
- `test`：验收/测试数据；
- `production`：公司正式数据。

正式数据不得拿来随便跑开发迁移实验。

## 2. Docker Compose 服务

建议：

```text
reverse-proxy
frontend
backend
worker
postgres
```

数据库、上传文件、备份均映射宿主持久目录。

## 3. 持久目录

使用环境变量配置，例如：

```text
DATA_ROOT=/volume1/docker/songmao-platform
UPLOAD_ROOT=${DATA_ROOT}/uploads
BACKUP_ROOT=${DATA_ROOT}/backups
POSTGRES_DATA=${DATA_ROOT}/postgres
```

实际绿联路径以设备可用目录为准，但代码不得出现这些硬编码路径。

## 4. 网络

- PostgreSQL 只在 Docker 内部网络暴露；
- 对用户只暴露 HTTPS 端口；
- 公司局域网试用阶段可先用局域网地址；
- 如需公网访问，必须开启 HTTPS 和合理的入口安全策略；
- 不把 FastAPI 调试端口直接暴露到公网。

## 5. HTTPS/域名

有域名时建议：

`manage.<company-domain>`

反向代理负责 TLS。没有域名的早期内网测试，可用 NAS 局域网 IP，但生产外网不允许 HTTP 明文登录。

## 6. 数据备份

### 每日

- PostgreSQL 逻辑备份（`pg_dump` 自定义格式或等价方案）；
- 保留至少最近 30 个日备份；
- 上传文件/CRM附件做增量或目录级备份。

### 每周

- 至少一份备份复制到与生产盘不同的位置；
- 可使用 NAS 的第二存储、外置盘或对象存储；
- 不允许“生产数据库和唯一备份在同一块盘”。

### 每月

- 月度长周期备份建议保留 12 份。

## 7. 恢复目标

V1 建议目标：

- RPO：<= 24 小时；
- RTO：<= 4 小时（公司小规模内部系统的务实目标）。

后续业务依赖更强再提高标准。

## 8. 备份恢复脚本

项目应提供：

- `scripts/backup_db.sh`
- `scripts/restore_db.sh`
- `scripts/backup_files.sh`（或文档化方案）

脚本不得把数据库密码写死在仓库。

## 9. 日志

建议容器 stdout + 结构化日志，重要日志至少保留：

- 请求错误；
- 导入错误；
- worker 任务失败；
- 权限拒绝；
- 同步失败；
- 审计日志（数据库）。

为防 NAS 磁盘被日志吃掉，配置轮转和保留周期。

## 10. 更新发布流程

1. 测试环境构建新版本；
2. 自动测试；
3. 数据库备份；
4. 执行 migration；
5. 启动新容器；
6. 健康检查；
7. 关键页面冒烟测试；
8. 确认后关闭旧版本/完成更新。

不得直接进入 NAS 生产容器里手工改代码。那会让未来的人，包括未来的我们，产生合理的敌意。

## 11. 回滚

重大版本发布前：

- 保留上一镜像标签；
- 保留数据库发布前备份；
- migration 说明是否可降级；
- 如果 schema 已不可逆，采用数据恢复方案而不是幻想一个 `git revert` 能把数据库也变回昨天。

## 12. NAS -> 云迁移

准备：

- 数据库备份；
- uploads/attachments；
- `.env` 配置（密钥安全转移）；
- Docker 镜像/源码版本。

迁移验证：

- 用户登录；
- CRM 数据；
- 销售/财务 BI；
- 附件；
- 定时任务；
- HTTPS；
- 备份。
